# NCP HTTP API

The `ncp serve` runtime speaks JSON-RPC 2.0 over plain HTTP POST, with an SSE
discovery stream. Any language with an HTTP client can drive it — MCP hosts
use this transport automatically, but the contract below is public and stable
for programmatic clients (TypeScript orchestrators, shell scripts, CI jobs).

All examples assume:

```bash
ncp serve --host 127.0.0.1 --port 4242 --cwd /path/to/project
BASE=http://127.0.0.1:4242
```

## Endpoints

| Method | Path       | Purpose                                        |
|--------|------------|------------------------------------------------|
| GET    | `/healthz` | Liveness probe (no auth required)              |
| GET    | `/sse`     | SSE discovery stream (emits the RPC endpoint)  |
| POST   | `/mcp`     | JSON-RPC 2.0 requests (also accepts `/message`)|

## Authentication

No token is required on loopback by default. When `[server].auth_token` is set
in `.ncp/config.toml` (generated by `ncp init`), via `NCP_AUTH_TOKEN`, or via
`ncp serve --auth-token`, every `/mcp` and `/sse` request must carry:

```bash
AUTH="Authorization: Bearer $TOKEN"
```

Unauthenticated requests receive `401 {"error": "unauthorized"}`. Request
bodies over 10 MB receive `413`. CORS headers are only emitted for origins
passed via `--cors-origin` (none by default — browsers cannot call the API).

`ncp serve` refuses to start on a non-loopback host without a token. The server
also rejects, before any tool runs:

| Condition | Response |
|-----------|----------|
| `POST` whose `Content-Type` is not `application/json` | `415 {"error": "unsupported_media_type"}` |
| `Origin` header that is neither same-origin nor allowed by `--cors-origin`, on `POST`, `/api/*`, `/events` and `/sse` | `403 {"error": "forbidden_origin"}` |
| Loopback bind and a `Host` header other than `localhost`, `127.0.0.1` or `[::1]` | `403 {"error": "forbidden_host"}` |
| Negative or non-numeric `Content-Length` | `400 {"error": "invalid_content_length"}` |

Requests with no `Origin` header (curl, MCP hosts) are unaffected. A connection
that sends or reads nothing for 30 seconds is closed; `/sse`, `/events` and a
blocking `ncp_wait_whispers` are not subject to that limit.

`ncp_record_outcome` requires `0 < weight <= 1`. A caller-supplied `base_trust`
is capped at the default trust for the declared `src`.

## Principals

By default the server has at most one shared token, and every tool trusts the
agent identity the caller declares (`agent_id`, `written_by`, `from`, ...):
anyone holding the token can act as any agent, rewrite another agent's
`owns`/`must_not`, write `src=user_verified`, record outcomes for any chunk,
and read or write any pipeline. **Principals** are the opt-in fix: each bearer
token maps to one principal with a fixed `agent_id`, an optional pipeline
allowlist and a set of capabilities, and the server derives the acting
identity from the token.

```toml
# .ncp/config.toml -- one table per token
[principals.router]
token_env = "NCP_TOKEN_ROUTER"     # read the token from this env var at startup
agent_id = "router"
capabilities = ["admin", "verify", "record_outcome"]

[principals.executor]
# hex SHA-256 of the token:  printf %s "$TOKEN" | sha256sum
token_sha256 = "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"
agent_id = "executor"
pipelines = ["pipe_payment"]       # omit to allow every pipeline
capabilities = []

[principals.validator]
token_env = "NCP_TOKEN_VALIDATOR"
agent_id = "validator"
capabilities = ["record_outcome"]
```

Each principal needs `agent_id` and exactly one of `token_sha256` (the token
is never stored in plaintext; a `token` key is refused) or `token_env` (the
secret stays out of the file). `pipelines`, if present, must be non-empty.
Capabilities:

| Capability | Grants |
|------------|--------|
| `verify` | writing `src="user_verified"` (`ncp_write_memory`, `ncp_post_turn` memory chunks) and `ncp_verify_memo` |
| `record_outcome` | calling `ncp_record_outcome` |
| `admin` | acting as any `agent_id` (router/orchestrator processes, the bundled UI), recording outcomes that credit its own chunks, turn-only outcomes, and unscoped `GET /api/*` reads |

An invalid `[principals]` table (unknown key or capability, malformed hash,
unset `token_env` variable, two principals with the same token) stops the
server from starting. With principals configured, `ncp serve` may bind to a
non-loopback host without `[server].auth_token`.

**Rules, when at least one principal is configured** (HTTP transport):

1. **Authentication.** Every `/mcp`, `/sse`, `/events` and `/api/*` request
   must carry a token that maps to a principal, on loopback too; otherwise
   `401`. If `[server].auth_token` is also set, that shared token maps to an
   implicit principal named `legacy_auth_token` with all three capabilities
   and no pipeline limit (the server prints a note at startup). Remove it once
   every client has its own token. A principal may not reuse the shared token.
2. **Identity comes from the token.** For every tool, each argument that names
   the acting agent must equal the principal's `agent_id`; a different value
   is rejected (never silently replaced), and an omitted one is filled in.
   `admin` principals may pass any value. The bound arguments:

   | Tool | Bound arguments |
   |------|-----------------|
   | `ncp_get_context`, `ncp_post_turn` | `agent_id` |
   | `ncp_post_turn` | `memory_chunks[].written_by` (omitted means `agent_id`) |
   | `ncp_write_memory` | `written_by`, `owner` (checked if given, never filled) |
   | `ncp_emit_whisper` | `from` |
   | `ncp_wait_whispers`, `ncp_overview`, `ncp_fetch` | `agent_id` |
   | `ncp_task` (every action) | `agent_id` |
   | `ncp_record_decision`, `ncp_compile_decision_query` | `agent_id` |
   | `ncp_remember` | `written_by` |

   Also: a `chunk_id` (`ncp_write_memory`, `memory_chunks[].chunk_id`) that
   names an existing chunk written by someone else is rejected, because the
   write would overwrite it; and `supersedes` may only name the principal's
   own chunks. Task mutations by `task_id` remain gated by the lease token.
3. **Pipeline ACL.** A principal with `pipelines` must pass an allowed
   `pipeline_id` to every tool that takes one; a call that **omits**
   `pipeline_id` is rejected rather than defaulted (an omitted pipeline means
   the unscoped/global scope, which is outside the allowlist). In addition:
   `ncp_task` actions by `task_id` are checked against the task's stored
   pipeline; `ncp_overview` must pass `pipelines` naming only allowed ones;
   memo tools must use `task`/`context`/`pipeline_id` rather than an explicit
   `signature`; `ncp_get_decision` returns `{"found": false}` for a decision in
   another pipeline; `ncp_record_outcome` chunks (and a linked `decision_id`)
   must be in allowed pipelines. The same holds for ids that reach another
   record: an `ncp_get_context` `recent` ref must name a turn in an allowed
   pipeline; `ncp_post_turn` `retrieved_chunk_ids` must be chunks in allowed
   pipelines (global-scope chunks excepted); a `dissent` whisper's `ref` must
   be a chunk in an allowed pipeline; and an `ncp_task` `parent_task_id` must
   be a task in an allowed pipeline.
4. **Capabilities.** `src="user_verified"` needs `verify`; `ncp_record_outcome`
   needs `record_outcome`. A non-admin principal must name explicit
   `chunk_ids` (turn-only outcomes are resolved inside the store, where
   authorship cannot be checked first), every id must be a live chunk, and
   none may have been written by the principal itself; nor may it link an
   outcome to its own `decision_id`. A pipeline-limited admin must also pass
   explicit `chunk_ids`. `ncp_improve` needs `admin`: consolidation merges
   near-duplicate chunks across authors, deleting the losers and aliasing
   their ids (and their outcome credit) to the keeper. `ncp_post_turn` with a
   `turn_id` that already exists replaces that turn record, so only the turn's
   own agent (or an admin) may post it again.
5. **Fetch budget.** `ncp_get_context` and `ncp_fetch` ignore the caller's
   `session_id`: the 3-per-turn `ncp_fetch` budget is keyed by principal
   (`principal:<name>`, or `principal:<name>:<pipeline>:<agent>` for admin).
   The `session_id` returned by `ncp_get_context` shows the key in use.
6. **GET endpoints.** `/api/*` reads that pass `pipeline_id` follow the
   pipeline ACL; reads without one (and `/api/overview`, which spans
   pipelines) require `admin` and no pipeline limit. `/events` binds
   `agent_id` like a tool argument (filled in when omitted, `403` on a
   mismatch, admin excepted) and requires an allowed `pipeline_id` for a
   pipeline-limited principal. `/sse` only needs a valid token. Denials are
   `403 {"error": "forbidden", "detail": "..."}`. The bundled UI therefore
   needs an admin token (or a pipeline-scoped token and a `pipeline_id`).

A denied tool call returns JSON-RPC error `-32003` with a message starting
`Forbidden:` and naming the argument and principal.

**stdio** (`ncp serve-stdio`, and hosts that spawn the server as a
subprocess) has no bearer token and applies no principals: it stays
unauthenticated-local, trusted like any process that can open the store file
directly. Use HTTP when agents must not be able to act as each other.

**Limits.** This is bearer-token identity: it binds a connection to a
principal; it is not per-message signing (combine with
`[identity].require_signatures` for that), and anyone holding a token is that
principal. It does not stop a principal from writing false or persuasive
content under its own name, and within an allowed pipeline the read APIs
(`/api/whispers`, `/api/chunks`, ...) show every agent's data. An agent
chooses its own `retrieved_chunk_ids`, so an admin recording a turn-only
outcome credits whatever chunks that turn declared, the agent's own included.
`target` on a whisper and `assign_to` on a task may name any agent. A
misspelled table name (for example `[principal.x]`) is not detected and leaves
principals off; `ncp doctor` does not check for it. When no
principal is configured, everything above is off and the server behaves
exactly as described in [Authentication](#authentication).

## List tools

```bash
curl -s $BASE/mcp -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 1, "method": "tools/list"
}'
```

Returns the enabled tool catalog, each tool with a JSON Schema under
`inputSchema`. The `core` profile advertises `ncp_get_context`,
`ncp_write_memory`, `ncp_emit_whisper`, `ncp_post_turn` and `ncp_fetch`. The
full profile adds `ncp_record_outcome`, `ncp_record_decision`,
`ncp_get_decision`, `ncp_compile_decision_query`, `ncp_overview`,
`ncp_remember`, `ncp_recall` and `ncp_improve`, plus these conditional tools:

- `ncp_wait_whispers` — unless `[notify].enabled = false`.
- `ncp_task` — only when `[tasks].enabled = true`.
- `ncp_lookup_memo`, `ncp_record_memo`, `ncp_verify_memo` — only when
  memoization is enabled (`[memoization].enabled`, off by default).

The authoritative list is `MCP_TOOLS` in `ncp/mcp/server.py`;
`tests/test_docs_tool_catalog.py` fails if a tool is missing from this file.

## Tool calls

All tool calls share one shape; results arrive as MCP content with a single
JSON-encoded text item:

```json
{"jsonrpc": "2.0", "id": N, "method": "tools/call",
 "params": {"name": "<tool>", "arguments": { ... }}}
```

**Unwrapping the result.** The tool payload is *not* on `result` directly — it
is a JSON-*encoded string* nested at `result.content[0].text`. You must parse
that inner string to get the object the sections below describe. Reading
`result` directly is the most common first-integration mistake: writes look
like they succeeded (the return value is simply ignored) while reads come back
empty with no error.

```javascript
const rpc = await resp.json();
const payload = JSON.parse(rpc.result.content[0].text);  // <- the actual result
// payload.context, payload.session_id, payload.written, ...
```

```bash
# jq equivalent
curl -s ... | jq -r '.result.content[0].text | fromjson'
```

### ncp_get_context — assemble the bounded turn context

```bash
curl -s $BASE/mcp -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 2, "method": "tools/call",
  "params": {"name": "ncp_get_context", "arguments": {
    "agent_id": "executor", "role": "build",
    "task": "fix_payment_bug", "slot": "payment", "intent": "advance",
    "pipeline_id": "pipe_demo",
    "max_tokens": 840, "ctx_used": 0.4
  }}}'
```

The decoded result contains:

- `context` — the assembled pidgin block to inject into the model prompt
- `session_id` — pass to `ncp_fetch` to share the fetch budget
- `pending_whisper_ids` — whisper ids consumed this turn; pass them to
  `ncp_post_turn` to acknowledge (at-least-once delivery: unacked whispers
  are redelivered next turn)
- `retrieved_chunk_ids` — ids of the stored chunks assembled into `context`;
  pass them to `ncp_post_turn` as `retrieved_chunk_ids` so a later
  `ncp_record_outcome(turn_id=...)` credits the memory that informed the turn
- `telemetry` — eviction counts, `fetch_budget_remaining`, and a `fetch_hint`
  when relevant context was evicted under the token budget
- `context_policy` — only when the request named one: the applied policy's
  `name`, `version`, `sha256` and `max_tokens_cap`, plus
  `max_tokens_capped_from` when an explicit `max_tokens` was lowered to the cap

Pass `"context_policy": "<name>"` to assemble this request under a
`[context_policies.<name>]` entry (see `docs/NCP_CONTEXT_POLICY.md`). Unknown
or invalid policies return a JSON-RPC error; omitting it keeps the deployment
behavior unchanged.

Conscious state (`recent`, `tried`, `failed`, `drift_score`, …) is hydrated
server-side from the latest `ncp_post_turn` snapshot for this
`(pipeline_id, agent_id)`; explicit arguments override hydrated values.

### ncp_post_turn — record the turn and acknowledge whispers

```bash
curl -s $BASE/mcp -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 3, "method": "tools/call",
  "params": {"name": "ncp_post_turn", "arguments": {
    "agent_id": "executor", "role": "build",
    "task": "fix_payment_bug", "slot": "payment", "intent": "advance",
    "pipeline_id": "pipe_demo",
    "result_summary": "null_guard_added_at_line_142",
    "result_full": "Applied null guard at PaymentProcessor.java:142; tests pass.",
    "ack_whisper_ids": []
  }}}'
```

Returns `{"posted": true, "turn_id": "...", "acknowledged_whisper_ids": [...]}`.
This is what makes recent-ref continuity, `ncp cost`, and `ncp status` work.

Optional `retrieved_chunk_ids` (array of strings, from `ncp_get_context`) and
`memory_chunks` are linked to the turn (relations `retrieved` and `wrote`;
dedup-suppressed chunks are not linked). `ncp_record_outcome` with only a
`turn_id` then resolves to those linked chunks, plus any chunk whose legacy
`caused_by` equals the turn id.

### ncp_write_memory — persist a durable chunk

```bash
curl -s $BASE/mcp -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 4, "method": "tools/call",
  "params": {"name": "ncp_write_memory", "arguments": {
    "content": "constraint: retryCount may be null for ACH trial customers",
    "layer": "semantic", "src": "tool_result",
    "written_by": "executor", "pipeline_id": "pipe_demo"
  }}}'
```

`base_trust` defaults by `src` (`user_verified` 0.95, `tool_result` 0.80,
`synthesis` 0.70, `agent_inferred` 0.60, `subcon_retrieved` 0.55) and may be
set explicitly.

Content is filtered at ingestion (ANSI codes, duplicate lines, and boilerplate
are stripped). A clean write returns:

```json
{"written": true, "chunk_id": "..."}
```

When filtering reduced the content, the response additionally carries
`filtered`, `reduction_ratio`, and — for originals under 2000 chars — a
`raw_ref` chunk id pointing at the stored unfiltered copy (retrievable via
`ncp_fetch`):

```json
{"written": true, "chunk_id": "...", "filtered": true,
 "reduction_ratio": 0.42, "raw_ref": "raw_..._1718900000000"}
```

`reduction_ratio` is the fraction of content removed (rounded to 3 decimals).
The `raw_ref` chunk is written with low trust (0.1) so the filtered chunk wins
ranking while the original remains recoverable.

### ncp_emit_whisper — signal another agent

```bash
curl -s $BASE/mcp -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 5, "method": "tools/call",
  "params": {"name": "ncp_emit_whisper", "arguments": {
    "from": "executor", "target": "reviewer", "type": "share",
    "payload": "fix applied to PaymentProcessor.java, please review",
    "confidence": 0.9, "pipeline_id": "pipe_demo", "ttl_seconds": 1800
  }}}'
```

`target: "*"` broadcasts to every agent in the pipeline (each receives it
once). Plain-text payloads for `share`/`request`/`dissent` are wrapped into
the required JSON shape server-side. Dissent remains non-broadcast: a
`dissent` call with `target: "*"` is rejected.

`payload` is required and supports an additive compatibility union:

- Legacy string payloads remain supported for the current major version. Their
  current normalization is retained, including plain-text wrapping for
  `share`/`request`/`dissent`; no removal version is planned until provider
  telemetry shows that legacy use is negligible.
- Structured-v1 objects are recommended. `share` and `request` require a
  HandoffPayload (`ask`, optional `files` and `slice`); `dissent` requires a
  DissentPayload (`issue`, optional `alternatives`); `alert` requires
  `alert_code` and `description`; `world_check` requires `anchor_intent` and
  `detected_drift`; `progress` requires a ProgressPayload (`status`, optional
  `pct` and `note`) and `result` a ResultPayload (`status`, `summary`, optional
  `result_chunk_ids` and `turn_id`). `progress`/`result` accept structured
  payloads only. An object whose shape does not match its `type` is rejected.

Structured-v1 values are stored as sorted, compact JSON. A successful response
includes `whisper_id` and `payload_format` (`"legacy"` or `"structured-v1"`),
plus `thread_id` when the whisper is threaded. If `signature` is provided, the
response also includes `verified`; signatures cover the exact normalized
payload that is stored, rather than the input object's key order.

**Request/reply threads.** A `share`/`request` opens a thread keyed by its own
`whisper_id`; the receiver sees it as `id:<whisper_id>` in its
`[NCP:WHISPERS]` entry. Reply with `progress`/`result` and `in_reply_to` set to
that id:

```bash
curl -s $BASE/mcp -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 5, "method": "tools/call",
  "params": {"name": "ncp_emit_whisper", "arguments": {
    "from": "reviewer", "target": "executor", "type": "result",
    "payload": {"status": "failed", "summary": "race in retry loop",
                "result_chunk_ids": ["sub_9c1"]},
    "confidence": 0.8, "pipeline_id": "pipe_demo", "in_reply_to": "wsp_3f2a"
  }}}'
```

`progress`/`result` require `in_reply_to`, `thread_id` or `task_id` and cannot target
`"*"`. A reply joins its parent's thread if the parent is still queued and
otherwise uses `thread_id = in_reply_to`, so replying after acknowledging the
request is fine. A newer `progress` on the same thread from the same sender
replaces the older undelivered one. `result` is delivered regardless of
`min_confidence` and ordered right after `alert`. `in_reply_to`/`thread_id`
are unsigned routing metadata.

**Task-linked reports.** `progress`/`result` may instead carry `task_id` (see
`ncp_task` below). The server then requires `[tasks].enabled = true`, `from`
to be the task's current owner, the task to be `claimed`, and `pipeline_id` to
match the task's; otherwise the call is rejected. Workers normally do not need
this: `ncp_task` `heartbeat`/`complete` emit the linked whisper for them.

### ncp_wait_whispers — wait for a doorbell

A long-poll that blocks until a whisper is queued for the agent, or the
timeout elapses. It only peeks: it never drains, acknowledges, or returns a
payload. Follow it with `ncp_get_context`.

```bash
curl -s $BASE/mcp -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 5, "method": "tools/call",
  "params": {"name": "ncp_wait_whispers", "arguments": {
    "agent_id": "router", "pipeline_id": "pipe_demo",
    "timeout_seconds": 30, "types": ["result"], "thread_id": "wsp_3f2a"
  }}}'
# {"ready": true, "timed_out": false,
#  "whispers": [{"whisper_id": "wsp_9d1", "type": "result", "from": "reviewer",
#                "thread_id": "wsp_3f2a", "in_reply_to": "wsp_3f2a",
#                "task_id": null}]}
```

`timeout_seconds` defaults to 30 and is clamped to
`0..[notify].max_wait_seconds`; `0` is a non-blocking check. `types` and
`thread_id` are optional filters. The tool is hidden in the `core` profile and
when `[notify].enabled = false`.

### GET /events — SSE doorbell stream

```bash
curl -N "$BASE/events?agent_id=router&pipeline_id=pipe_demo" -H "$AUTH"
# event: ready
# data: {"queued": 1}
#
# event: whisper
# data: {"event":"whisper","whisper_id":"wsp_9d1","type":"result","from":"reviewer","target":"router","pipeline_id":"pipe_demo","thread_id":"wsp_3f2a","task_id":null,"status":null,"created_at":1793500000.0}
#
# : keepalive
```

Same bearer auth and CORS handling as `/mcp`. `agent_id` is required (`400`
without it); `pipeline_id` is optional. Frames never carry whisper payloads:
call `ncp_get_context` to receive them. When the task ledger is on, `event: task` frames
(same fields, `whisper_id` null, `status` set) announce a task that failed by
lease expiry (to its creator) or was cancelled while claimed (to its owner);
they carry no title or summary. Concurrent streams are capped by
`[notify].max_subscribers` (default 64); above it the server returns `503` with
`Retry-After`. Reconnect and call `ncp_wait_whispers` with
`timeout_seconds: 0` to catch up on anything missed.

**Cross-process latency.** With the default in-process notifier, a whisper
written by a different process (another `ncp serve`, or a script on the same
database) does not ring the doorbell. `ncp_wait_whispers` and `/events` find it
by re-peeking the store every `[notify].poll_interval_seconds` (default 2.0,
`0` disables, minimum 0.25), so latency for such a write is up to about one
interval; same-process writes are still immediate. The fallback is off with the
Redis backend, and `event: task` frames are in-process-only.

### ncp_task — leased task ledger

Opt-in (`[tasks].enabled = true`), absent from the `core` profile. One tool,
eight actions. Owner actions (`heartbeat`, `release`, `complete`) must present
the `lease_token` returned by `claim`; a stale or expired token returns
`{"ok": false, "reason": "lease_lost"}` (HTTP 200, not an error) and the
worker must stop.

```bash
# Router: create a task and ask a worker to take it (also emits a request whisper)
curl -s $BASE/mcp -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": {"name": "ncp_task", "arguments": {
    "action": "create", "agent_id": "router", "pipeline_id": "pipe_demo",
    "slot": "review", "title": "review PR 142", "dedupe_key": "github:pr/142:review",
    "assign_to": "reviewer"
  }}}'
# {"created": true, "task": {"task_id": "tsk_9c1d2e3f4a5b", "status": "open", ...},
#  "assigned": true, "whisper_id": "wsp_3f2a"}

# Worker: claim (by task_id, or the oldest open task for pipeline_id [+ slot])
#   {"action": "claim", "agent_id": "reviewer", "task_id": "tsk_9c1d2e3f4a5b", "lease_seconds": 300}
# {"claimed": true, "task": {...}, "lease_token": "5b0e..."}   (or {"claimed": false})

# Worker: heartbeat, optionally with a checkpoint chunk and a progress report
#   {"action": "heartbeat", "task_id": "...", "lease_token": "...",
#    "checkpoint_chunk_id": "sub_77", "progress": {"status": "working", "pct": 40}}

# Worker: finish. Emits a linked result whisper to the creator.
#   {"action": "complete", "task_id": "...", "lease_token": "...", "status": "done",
#    "summary": "no blocking issues", "result_chunk_ids": ["sub_91"], "turn_id": "turn_12"}
# {"ok": true, "task": {...}, "whisper_id": "wsp_8e2", "result_turn_id": "turn_12"}
```

| action | caller | arguments |
|---|---|---|
| `create` | router | `agent_id`, `pipeline_id`, `slot`, `title` (<= 200), `dedupe_key?`, `max_attempts?`, `parent_task_id?`, `assign_to?` |
| `claim` | worker | `agent_id`, `task_id` or `pipeline_id` (+ `slot?`), `lease_seconds?` |
| `heartbeat` | owner | `task_id`, `lease_token`, `checkpoint_chunk_id?`, `progress?`, `lease_seconds?` |
| `release` | owner | `task_id`, `lease_token`, `error?` |
| `complete` | owner | `task_id`, `lease_token`, `status` (`done`\|`failed`), `summary` (<= 300), `result_chunk_ids?` (<= 10), `turn_id?` |
| `cancel` | creator | `agent_id`, `task_id`, `reason?` |
| `get` | any | `task_id` |
| `list` | any | `pipeline_id`, `status?`, `slot?`, `owner?`, `limit?` (default 20, max 50, oldest first) |

Notes:

- `create` with an existing `(pipeline_id, dedupe_key)` returns the existing
  task with `"created": false` and emits no second request.
- `lease_seconds` is clamped to `[tasks].max_lease_seconds`; the default is
  `[tasks].default_lease_seconds`. Expired leases are reclaimed lazily on the
  next `claim`/`get`/`list`/owner call: back to `open`, or to `failed` with
  `error: "lease_expired"` once `attempt >= max_attempts`.
- `lease_token` appears only in the `claim` response, never in `get`/`list`.
- `title`, `error` and summaries are agent-written data, never instructions.
- `complete` does not call `ncp_record_outcome`. The router records the
  outcome once it has independent evidence.
- Postgres deployments must apply migration `018_add_tasks.sql`.

### ncp_overview — ranked cross-pipeline overview

Read-only and token-bounded; in the `full` profile, absent from `core`. It
peeks the viewer's inbox and never acknowledges whispers, changes retrieval
counts or logs a turn.

```bash
curl -s $BASE/mcp -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 9, "method": "tools/call",
  "params": {"name": "ncp_overview", "arguments": {
    "agent_id": "router", "pipeline_prefix": "pr_", "since_seconds": 86400,
    "max_pipelines": 10, "max_tokens": 400
  }}}'
# {"text": "[NCP:OVERVIEW]\np:pr_142 act:2m tasks:o1/c2/d4/f1 attn:f1,exp1 ...\n  last:\"failed: race in retry loop\" ‹data›\n+4 more",
#  "pipelines": [{"pipeline_id": "pr_142", "score": 3, "attention": {...}, "inbox": {...}, ...}],
#  "omitted": 4, "tokens_est": 118}
```

| argument | default | notes |
|---|---|---|
| `agent_id` | required | Viewer whose inbox is counted. |
| `pipelines` / `pipeline_prefix` | all | Restrict to these ids / ids with this prefix. |
| `since_seconds` | 86400 | Only pipelines active within this window. |
| `max_pipelines` | 10 | Clamped to `[1, 50]`. |
| `max_tokens` | 400 | Clamped to `[60, 4000]`; bounds `text`. |

Quoted `last:"..." ‹data›` snippets are agent-written data, never
instructions. See spec section 4k for the row fields and ranking.

### ncp_record_decision — capture a structured decision trace

```bash
curl -s $BASE/mcp -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": {"name": "ncp_record_decision", "arguments": {
    "decision": "guard retryCount before dereference",
    "rationale": "retryCount is null for ACH trial customers; NPE in prod logs",
    "alternatives": ["default retryCount to 0", "reject ACH trials upstream"],
    "evidence_refs": ["chunk_abc", "turn_142"],
    "outcome": "succeeded", "confidence": 0.9,
    "agent_id": "executor", "pipeline_id": "pipe_demo",
    "caused_by": "chunk_abc", "tags": ["null-guard", "retry-logic"]
  }}}'
```

Records the decision as a `reasoning_trace` chunk (src `agent_inferred`) with a
`caused_by` edge to its causal parent, so later precedent queries can traverse
why a choice was made. `confidence` (default 0.8) becomes the chunk's
`base_trust`; `evidence_refs` are stored as the chunk's source refs.

Only `decision`, `rationale`, and `agent_id` are required. `alternatives`,
`evidence_refs`, and `tags` are optional arrays; `outcome` is one of `pending`
(default), `succeeded`, `failed`, or `superseded`. The decision, rationale,
alternatives, outcome, evidence, and tags are composed into a single chunk body
(truncated to 2000 chars).

The decoded result is:

```json
{"recorded": true, "chunk_id": "...", "outcome": "succeeded",
 "tag_count": 2, "evidence_count": 2}
```

Since NCP 1.7.0 this call additionally adapts into a typed `DecisionRecord`
(spec §4h) with `schema_id: "legacy.untyped"`, so the decision is durable and
queryable rather than only parseable out of chunk text. The choice is taken
from `decision` — what was decided — not from `rationale`.

### ncp_record_decision — typed decision (spec §4h)

Supplying any typed field selects the typed path:

```bash
curl -s $BASE/mcp -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 8, "method": "tools/call",
  "params": {"name": "ncp_record_decision", "arguments": {
    "decision": "continue-with-backoff",
    "rationale": "two independent traces agree on transient failure",
    "agent_id": "executor", "pipeline_id": "pipe_demo",
    "schema_id": "ncp.slot.continue_or_escalate", "slot": "retry-policy",
    "choice": "continue", "options": ["continue", "escalate", "stop"],
    "probs": {"continue": 0.8, "escalate": 0.15, "stop": 0.05},
    "confidence": 0.9, "backend": "system_one",
    "confidence_source": "backend_claimed",
    "state_hash": "<from ncp_compile_decision_query>",
    "chunk_ids": ["chunk_abc", "chunk_def"]
  }}}'
```

`schema_id` is required on the typed path. `schema_version` defaults to the
current registered version; an explicitly stale version is rejected. Zero
confidence is preserved. A registered schema validates the choice and the
prob keys; a mismatch returns
`{"recorded": false, "error": "schema_mismatch", "details": "..."}` and writes
no row. On success `recorded` reports the typed row and `trace_chunk_written`
reports the legacy chunk separately — they differ when two decisions share
identical prose and the chunk hits write-time dedup.

### ncp_get_decision — read one typed decision

```bash
curl -s $BASE/mcp -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 9, "method": "tools/call",
  "params": {"name": "ncp_get_decision", "arguments": {
    "decision_id": "dec_3f2a91c4be07"
  }}}'
```

Returns `{"found": true, "decision": {...}}` in canonical form — identical
bytes across processes for the same stored decision.

### ncp_compile_decision_query — compile a decision packet

```bash
curl -s $BASE/mcp -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 10, "method": "tools/call",
  "params": {"name": "ncp_compile_decision_query", "arguments": {
    "agent_id": "executor", "role": "implementer",
    "task": "fix-auth", "slot": "retry-policy", "intent": "unblock-login",
    "schema_id": "ncp.slot.continue_or_escalate",
    "pipeline_id": "pipe_demo", "k": 6
  }}}'
```

Returns `state` (conscious fields plus bounded evidence), `questions` the
backend must answer, a stable `state_hash`, up to three `precedents`, advisory
`joint_confidence` and `contradiction_mass`, and `escalate` with
`escalate_reasons` from a closed set. Makes zero provider calls.

`escalate_reasons` never names a model: NCP says *why* a stronger backend is
warranted, and the host decides *which one*. When `escalate` is false and a
`suggested_choice` is present, a prior decision over the same state is
available for reuse — NCP still does not apply it. Reuse requires the current
schema version and a choice valid under that schema. A linked failed, missing,
or unreadable outcome blocks reuse, regardless of confidence or outcome age.
The packet includes `schema_version` for clients recording the decision.
Compilation suppresses automatic embedding calls on every store backend.

### Ontology tools (opt-in)

Operational guide (configuration, auth model, rollout, limitations):
[`NCP_ONTOLOGY.md`](./NCP_ONTOLOGY.md).

Listed only with `[ontology] enabled = true` and the `full` tool profile.
Storage is the NCP store itself (`[ontology] store = "inherit"`): SQLite or
PostgreSQL/pgvector (see [Ontology storage backends](#ontology-storage-backends));
on any other backend the tools answer `{"ok": false, "error": {"code": "disabled"}}`. With the ontology disabled (the default) `tools/list` and every
other tool response are byte-for-byte unchanged, and calling an ontology tool
returns the ordinary `-32601 Tool not found` error.

| Tool | Purpose |
|------|---------|
| `ncp_ontology_capabilities` | enabled flag, provider, packs with versions and entity/relation types, limits, tool names. Disabled: `{"ok": true, "enabled": false, "version": "1"}` |
| `ncp_ontology_query` | resolve one seed (`entity_id`, or exact `key`: canonical key, then alias; `entity_type` narrows), then bounded traversal. Several matches → `resolved: false` with `ambiguity.candidates`, never a guess. `max_hops`/`max_nodes`/`max_edges` are clamped to the config (with a `clamped:` warning); `verified_only` defaults to the config |
| `ncp_ontology_explain` | one relation, every evidence row (`status`, `live`) and `validity` (`active`, `evidence_supported`, `verified_and_supported`). Read-only |
| `ncp_ontology_assert` | `kind: "entity"` (+ `expected_version`) or `kind: "relation"` (requires `idempotency_key` and `observed_at`; `created_by` is always the caller) |
| `ncp_ontology_revoke` | revoke a relation (idempotent, audited) |

```bash
curl -s $BASE/mcp -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "jsonrpc": "2.0", "id": 11, "method": "tools/call",
  "params": {"name": "ncp_ontology_query", "arguments": {
    "pipeline_id": "pipe_demo", "key": "checkout", "entity_type": "Service", "max_hops": 2
  }}}'
```

**Namespaces and permissions.** `pipeline_id` names the namespace (a pipeline,
or `global`). Reads see that namespace plus `global` (default `global`); writes
require `pipeline_id` and target exactly it. Permissions never come from tool
arguments; they come from the authenticated principal:

- read + write on pipelines in the principal's allowlist (any pipeline without
  one); `global` is readable by every principal, writable only with `admin`;
- `verify` (assert or change a `verified` relation) if the principal has
  `verify`; `admin` (global writes, revoking another principal's relation) if
  it has `admin`;
- no principal (stdio, or HTTP without `[principals]`): principal `local` with
  `[ontology] unauthenticated_capabilities` (default `["read", "write"]`, so
  verified relations and global writes are denied).

A pipeline outside the allowlist is rejected with `-32003 Forbidden` before the
handler runs, like other pipeline-scoped tools.

**Results.** Success: `{"ok": true, ...}`. Failure:
`{"ok": false, "error": {"code": ..., "message": ...}}` with `code` one of
`conflict` (idempotency key reused with another payload, revision mismatch),
`forbidden`, `invalid`, `not_found`, `disabled`, `limit` (a hard bound such as
more than 100 `relation_types` or 32 evidence refs). An object outside the
caller's readable scope is reported exactly like a missing one (`not_found`);
an authorization failure never falls back to an unscoped query.

**Policy details.** A relation is active only inside
`[valid_from, valid_until)`: future-dated relations are skipped by traversal,
cardinality checks and automatic context, but `ncp_ontology_explain` still
returns them (`in_validity_window: false`). Chunk evidence whose `valid_from`
is in the future is not live. Only the original asserter or an `admin` may
change an existing relation's `valid_from`/`valid_until` by re-asserting it.
The asserter may revoke its own relation, even a verified one, without
`verify`. `verified_only: false` is honored only when the server's
`[ontology] verified_only` is false or the caller has `verify`/`admin`;
otherwise it is forced to `true` with a `forced:` warning. Query/explain
redact relation attribute values whose key looks like a credential
(`password`, `secret`, `token`, `api_key`, `private_key`, `credential`) as
`[REDACTED]` unless the caller has `admin`.

### Ontology-aware context (opt-in)

With `[ontology] enabled = true`, `ncp_get_context` may append a
`[NCP:ONTOLOGY]` block of verified domain-graph paths (after memory, before
whispers) and returns an `ontology` metadata object. Disabled, or when the
request resolves to mode `off`, the response is byte-for-byte the legacy one
and has no `ontology` key.

- **Mode** (`[ontology] retrieval_mode`, default `auto`): `off`, `auto` (expand
  only on a positive trigger) or `always`. A request may pass `"ontology":
  false` (or `{"mode": "off"}`) to opt out; `{"mode": "auto"|"always"}` needs
  `admin` and is otherwise ignored with a warning.
- **Trigger (`auto`)**: entity keys/aliases/ids in `task`/`slot`/`intent` are
  resolved exactly in the caller's scope. Expansion needs a uniquely resolved
  entity plus relationship intent (depends, upstream, consumer, owner, impact,
  pack relation names) or diagnostic intent (why, lag, outage, root cause), or
  two supporting signals (matching type name, memory chunk mentioning the
  entity). Ambiguous aliases are never guessed. Budgeted by `trigger_max_ms`.
- **Expansion**: bounded traversal (`max_hops`/`max_nodes`/`max_edges`,
  `graph_timeout_ms`), always verified-only; each relation needs a live chunk
  readable by the caller or an external attestation. Paths are ranked
  `0.40*query_relevance + 0.25*evidence_quality + 0.15*freshness +
  0.10*distance + 0.10*diversity` and serialized as compact statements with
  evidence chunk citations (`ev:`), never entity/relation attributes. The block
  is limited to `max_graph_tokens` inside the caller's `max_tokens`; the
  conscious block and budget header are never evicted for it. Cited chunks are
  not added to `retrieved_chunk_ids`.
- **Failures**: timeouts and backend errors return ordinary context with
  `fallback_reason` (or fail the call when `fail_mode = "closed"` /
  `fallback_to_memory = false`); an authorization failure fails closed.
- **Metadata**: `ontology_triggered`, `reason_code`, `candidate_count`,
  `verified_path_count`, `latency_ms`, `graph_tokens`, `fallback_reason`,
  `signals`, `entities`, `paths` (ids, labels, relation types, evidence ids),
  `omitted`, `warnings`. Raw query text is never included. Under
  `response_max_tokens` the graph block is shed before memory, and once the
  other diagnostics are gone the metadata is cut to its core telemetry
  (`truncated.dropped` lists `ontology_detail`).
- Enrichment reads an existing ontology but never creates its tables: under
  the `core` tool profile the ontology store stays uninitialized
  (`reason_code: "ontology_uninitialized"`) until an ontology tool runs.

### Ontology storage backends

Both backends implement the same store API with the same semantics: equal
ordered graph results, status transitions, revisions, idempotency/conflict
outcomes, cardinality and cycle rules, evidence liveness, scope isolation and
error codes (`tests/test_ontology_parity.py` runs one scenario suite against
both and requires identical transcripts).

- **SQLite** (`SQLiteStore`): `ontology_*` tables in the NCP database file;
  writers serialize on `BEGIN IMMEDIATE`.
- **PostgreSQL** (`PgvectorStore`): `{schema}.{table_prefix}ontology_*` tables
  in the pgvector store's own schema and prefix, created by an additive,
  versioned migration the first time the ontology is used (a plain
  `PgvectorStore` and a disabled ontology create nothing). Key columns use
  `COLLATE "C"` so ordering matches SQLite byte order. Writes run in `READ
  COMMITTED` behind transaction-scoped advisory locks -- one per
  `(tenant, pipeline)` write scope for relation writes (so cardinality, cycle
  and idempotency checks are race-free while pipelines write in parallel),
  one per relation id and per entity id -- with a bounded `lock_timeout`.
  Reads use one `REPEATABLE READ, READ ONLY` snapshot; `graph_timeout_ms` /
  `trigger_max_ms` become `SET LOCAL statement_timeout` inside that
  transaction. `ontology_events` is append-only (a trigger rejects `UPDATE`,
  `DELETE` and `TRUNCATE`). Chunk evidence is checked against
  `{schema}.{table_prefix}chunks` and fails closed if that table is absent.
- **Async hosts**: NCP's async runtime (`AsyncPgvectorStore`) covers only the
  post-turn write path and never assembles context, so the facade stays
  disabled for it. In-process async code can use
  `ncp.ontology.stores.AsyncPostgresOntologyStore`, a thin wrapper that runs
  the PostgreSQL store in worker threads (`asyncio.to_thread`) with identical
  results.

## Streaming

Pass `"stream": true` to `ncp_get_context`. Over HTTP the response is NDJSON:
one `{"type": "ncp_chunk", "section": ..., "index": ..., "text": ...}` line
per section (`conscious`, `subconscious`, `ontology` when enriched, `whispers`,
`budget_header`),
terminated by the standard JSON-RPC result line. All sections derive from a
single assembly pass, so the concatenated stream matches the non-streaming
`context` exactly.

## Content negotiation (SSE responses)

`POST /mcp` honors the `Accept` header so the endpoint behaves as a stateless
[Streamable HTTP](https://modelcontextprotocol.io) MCP server:

- `Accept: application/json` (or any value that includes it) — the JSON-RPC
  result is returned in the response body. This is the default and matches
  what the MCP SDK sends, so MCP hosts work without extra configuration.
- `Accept: text/event-stream` (without `application/json`) — the response is
  an SSE stream. A normal call yields a single `event: message` carrying the
  JSON-RPC result; a `"stream": true` call yields one `event: ncp_chunk` per
  section followed by the `event: message` result.

There is no `Mcp-Session-Id` header: each `POST /mcp` is self-contained. The
`GET /sse` endpoint is discovery-only — it advertises the RPC path and emits
keepalives, but does not carry JSON-RPC responses.

## Memory visualization UI

`ncp serve` also hosts a read-only web UI at `/ui` (e.g.
`http://127.0.0.1:4242/ui`) for inspecting what the bus remembers: a
per-agent turn timeline with whisper traffic, a filterable memory-chunk
browser with trust badges and tombstone/supersede state, a whisper inbox
with TTL countdowns, an interactive memory graph over `caused_by`/
`supersedes` and typed chunk edges, and a stats view over store counts and
cost telemetry.
It is plain HTML/CSS/JS served from the package — no build step, no external
requests.

The UI polls a set of read-only JSON endpoints. These are plain `GET`
endpoints (not MCP tools — they do not appear in `tools/list`) and require
the same bearer token as `/mcp` when one is configured; the static `/ui`
shell itself is served without auth and prompts for the token in-browser.

| Endpoint        | Query params                                              | Backed by              |
|-----------------|-----------------------------------------------------------|------------------------|
| `/api/status`   | `pipeline_id`                                             | `status_detail()` + memo stats |
| `/api/chunks`   | `pipeline_id`, `layer`, `zone`, `src`, `written_by`, `limit` (≤200), `offset` | chunk listing |
| `/api/turns`    | `pipeline_id`, `limit` (≤200)                             | `recent_turns()`       |
| `/api/whispers` | `pipeline_id`, `target`, `include_expired`, `limit`       | whisper listing        |
| `/api/graph`    | `pipeline_id`, `limit`                                    | `graph_data()`         |
| `/api/cost`     | `pipeline_id`, `limit`                                    | `cost_summary()`       |
| `/api/overview` | `agent_id`, `prefix`, `since` (seconds), `max_pipelines` (1-50), `max_tokens` | `overview_rows()`; same payload as `ncp_overview` |

Responses are plain JSON objects (no JSON-RPC envelope, no
`result.content[0].text` unwrapping). Chunk listings include tombstoned and
superseded rows flagged as such rather than hiding them, matching the
store's bi-temporal honesty model. All endpoints are read-only: the UI
cannot write memory, emit whispers, or mutate trust.
